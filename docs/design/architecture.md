# rswebgl: архитектура ядра

Статус: этапы 1–5 сделаны, этап 6 — ресурсная часть glTF, ядро WebGL2 покрыто; идёт сцена на ECS (`ecs.md`, E1–E4 сделаны), затем PBR.

## 1. Зачем это всё

Rust не ускоряет WebGL: каждый GL-вызов из wasm всё равно уходит в JS, и стоит
он столько же, сколько из JS. Смысл библиотеки в другом:

1. **Глобальное состояние WebGL под контролем рендерера.** Пользователь
   описывает, что нарисовать, а не какие `bind*` вызвать. Ошибки класса «забыл
   привязать / кто-то перепривязал» становятся невозможными.
2. **Эффективная CPU-часть.** Сортировка, отсечение, трансформации, анимация,
   подготовка данных для GPU — в плотных массивах без GC и без аллокаций за
   кадр. Здесь Rust реально выигрывает у JS.
3. **Два равноправных API: Rust и JS.** Неизвестно, кто будет основным
   потребителем: Rust-код (если библиотека заменит рендерер в cgtools) или
   JS-приложения (если это будет отдельный продукт). Оба должны быть удобными,
   а не «JS — обёртка, написанная потом».

Чего в cgtools не хочется повторять: `Rc<RefCell<…>>` везде, из-за чего типы
не проходят в JS и под каждое использование пишется отдельная обёртка, и
невозможность что-то удалить, потому что на объект держат ссылки все подряд.

Честно о текущем rswebgl: пункт 1 сделан хорошо. Пункты 2 и 3 — нет. Все
хэндлы — общие `Rc` (сейчас `Rc<Inner>`), объект живёт, пока жив последний
клон, явного удаления нет; на каждый draw идут поиски по строкам и клоны `Rc`;
в JS каждый объект требует `.free()`. То есть ровно проблема cgtools. Этот
документ предлагает, как это переделать.

## 2. Принципы

1. **Ресурсы — числа, а не объекты.** Буфер, текстура, программа, меш — это
   хэндл `u32` с поколением. Всё состояние живёт в одном месте, внутри
   `Context`. Хэндл ничего не держит, его можно копировать, хранить в
   компоненте ECS, передать в JS, сериализовать.
2. **Время жизни явное.** `destroy(handle)` удаляет сразу. Обращение к
   удалённому хэндлу распознаётся по поколению: понятная ошибка вместо
   падения или тихого рисования мусором.
3. **Строки — на этапе настройки, числа — во время работы.** Имена униформ,
   блоков, атрибутов, компонентов ECS разрешаются в числовые id один раз. На
   горячем пути ни одной строки.
4. **Данные — плоские типизированные массивы в памяти wasm.** Параметры
   материалов, трансформации, компоненты ECS лежат в SoA-колонках. JS видит их
   как `Float32Array` поверх памяти wasm и пишет напрямую, без вызова на каждое
   значение.
5. **Ноль аллокаций за кадр** на горячем пути: заполнение draw-списка,
   сортировка, отправка.
6. **Одно ядро, два фасада.** Ядро на Rust с типами, которые без потерь
   проходят через wasm-bindgen. Rust-удобства и JS-фасад — тонкие слои сверху.

## 3. Слои

```
┌──────────────────────┐  ┌──────────────────────┐
│  JS-фасад (wasm)     │  │  Rust-удобства        │
│  числа, TypedArray,  │  │  типизированные id,   │
│  .d.ts с брендами    │  │  трейты, glam, RAII   │
└──────────┬───────────┘  └──────────┬───────────┘
           └─────────────┬───────────┘
              ┌──────────▼──────────┐        ┌────────────────────┐
              │  renderer (ядро)    │◄───────│  ecs (отдельно)    │
              │  ресурсы, программы,│ draw-  │  мир, компоненты,  │
              │  параметры, draw-   │ списки │  системы, иерархия │
              │  списки, кэш GL     │        └─────────┬──────────┘
              └──────────┬──────────┘                  │
              ┌──────────▼─────────────────────────────▼──┐
              │  foundation: хэндлы и пулы, раскладки      │
              │  (схемы), колонки с JS-видами, грязные     │
              │  диапазоны                                 │
              └────────────────────────────────────────────┘
```

Пересечение с ECS как раз в нижнем слое. Рендереру и ECS нужны одни и те же
четыре вещи: id с поколениями, описание раскладки полей по строковым именам,
плотные типизированные колонки, видимые из JS, и учёт изменений. Их делаем
один раз в `foundation`, и ни рендерер, ни ECS не изобретают своё.

ECS при этом не зависит от рендерера, а рендерер от ECS: компоненты хранят
хэндлы рендерера как обычные `u32`, а «система рендера» в ECS превращает
компоненты в draw-список. Можно пользоваться рендерером без ECS и ECS без
рендерера.

## 4. Foundation

### 4.1 Хэндлы и пулы

```rust
// 20 бит индекс (1M живых объектов на тип), 12 бит поколение.
#[repr(transparent)]
pub struct Handle(u32);

pub struct Pool<T> {
    slots: Vec<Slot<T>>,   // данные + поколение
    free: VecDeque<u32>,   // FIFO: слот переиспользуется как можно позже
}
```

- `u32`, а не `u64`: в JS это обычный `number`, а `u64` превратился бы в
  `BigInt`.
- **Что будет, когда поколения закончатся.** При каждом переиспользовании
  слота его поколение растёт на 1. Слот, у которого поколение дошло до
  максимума (4095), **выводится из оборота навсегда**: он больше не попадает в
  свободный список. Поэтому старый хэндл никогда не совпадёт с новым объектом
  — ни через тысячу, ни через миллион пересозданий. Это гарантия по
  построению, а не «маловероятно».
- Цена — выведенный слот занимает несколько байт и не переиспользуется.
  Чтобы исчерпать все слоты пула, нужно создать и удалить около 4 миллиардов
  объектов одного типа (2^20 слотов × 4096 поколений). Для GPU-ресурсов это
  недостижимо. Если пул всё же исчерпан, создание возвращает ошибку, как при
  нехватке памяти.
- **Уязвимость ли это?** Нет. Даже без вывода из оборота старый хэндл мог бы
  указать только на другой живой объект того же типа: нарисовалась бы не та
  текстура или удалился бы не тот буфер. Это логическая ошибка, а не порча
  памяти: доступ всё равно идёт через проверку индекса в безопасном Rust. И
  вызывать API может только код самой страницы, то есть границы привилегий
  тут нет. Вывод слотов из оборота закрывает и эту логическую ошибку.
- Для ECS (сущностей создаётся и удаляется на порядки больше, например
  частицы) `Handle` будет параметризован шириной: можно взять 53-битный id
  (точно представим как `number` в JS) — 32 бита индекс, 21 бит поколение.
  Решим в ECS-документе.
- В Rust поверх `Handle` типизированные обёртки: `TextureId`, `ProgramId`,
  `MeshId`, `Entity`… Перепутать текстуру с буфером нельзя.
- В JS это `number`, а в `.d.ts` — брендированные типы
  (`type TextureId = number & { readonly __brand: "Texture" }`), чтобы
  TypeScript тоже не дал их перепутать.
- Нулевой хэндл зарезервирован как «нет объекта».

Механизм поколений уже есть: я сделал его для потери контекста
(`context_loss.rs`). Там поколение одно на весь контекст, здесь — на слот.

### 4.2 Раскладки (схемы)

Описание структуры данных по именам:

```rust
pub struct Layout {
    fields: Vec<Field>,          // имя → тип, смещение, размер массива
    size: u32,
    rule: LayoutRule,            // Std140 | Packed | ...
}
```

Где используется одна и та же сущность:

- uniform-блоки (std140) — сейчас это `UboLayout` в `uniform_buffer.rs`;
- обычные униформы программы, прочитанные через `getActiveUniform`;
- схемы компонентов ECS, в том числе объявленные из JS строками:
  `world.defineComponent("Transform", { position: "vec3", rotation: "quat" })`.

Имена разрешаются в `FieldId` (индекс поля) один раз; дальше доступ только по
id.

### 4.3 Колонки и JS-виды

Плотный типизированный массив в памяти wasm плюс способ дать JS прямой вид на
него:

```rust
pub struct Column<T: Pod> { data: Vec<T>, /* + учёт изменений */ }
// JS: column.view() -> Float32Array поверх wasm-памяти, без копирования
```

Главная ловушка веба: **когда память wasm растёт, все существующие
`ArrayBuffer`-виды отсоединяются** и превращаются в массивы нулевой длины.
Поэтому:

- у памяти есть счётчик версий; виды отдаются через геттер, и JS-фасад
  перевыдаёт вид, если версия изменилась;
- в документации правило: не держать вид между кадрами, брать заново в начале
  кадра (это дёшево).

### 4.4 Учёт изменений

Сейчас `UniformBuffer` помечает один грязный диапазон `[lo, hi)`. Обобщаем:
битовая маска по блокам фиксированного размера (16 байт для std140, N
элементов для колонок). Нужна и для загрузки UBO и instance-буферов на GPU
(грузить только изменённое), и для ECS (запросы «изменилось с прошлого
кадра»).

## 5. Рендерер

### 5.1 Ресурсы

Все GL-объекты живут в пулах внутри `Context`:

| Ресурс | Что внутри | Заметки |
|---|---|---|
| `BufferId` | GL-буфер, размер, вид (index / generic) | |
| `TextureId` | GL-текстура, target, формат, размеры | |
| `RenderbufferId` | | |
| `FramebufferId` | аттачменты — хэндлы | |
| `ProgramId` | GL-программа + отражение (§5.3) | |
| `MeshId` | VAO + раскладка вершин + хэндлы буферов | по умолчанию владеет своими буферами |
| `StateId` | интернированный `RenderState` | одинаковые состояния → один id |
| `BindGroupId` | набор параметров (§5.4) | |

`ctx.destroy(id)` удаляет GL-объект сразу. WebGL сам корректно обрабатывает
удаление объекта, который ещё к чему-то привязан.

Зависимости между ресурсами — хэндлы, а не владение. Два режима:

- **Меш владеет своими буферами** (по умолчанию): `destroy(mesh)` удаляет и
  их.
- **Общие буферы.** Буфер создаётся отдельно и подключается к нескольким
  мешам (общий index-буфер, один большой вершинный буфер на много мешей с
  разными смещениями). Пул ведёт счётчик использований — это просто число в
  слоте, а не `Rc`. `destroy(buffer)`, пока буфер используют меши, не
  удаляет его сразу, а помечает «к удалению»: хэндл буфера сразу становится
  невалидным для нового использования, а GL-объект удаляется, когда
  уничтожен последний меш, который на него ссылается. Так нет ни висячих
  ссылок, ни утечек, а удаление остаётся явным.

Тот же механизм «удалить, когда освободится» подходит для текстур в
аттачментах framebuffer и в группах параметров.

Потеря контекста: старые хэндлы становятся невалидными (поколения всех слотов
сдвигаются). Поскольку `Context` хранит описания ресурсов, позже можно
сделать автовосстановление: пересоздать объекты по описаниям, если включено
хранение CPU-копий данных. В первой версии — как сейчас, через `on_restored`.

### 5.2 Постоянный кэш состояния GL

Раньше трекер состояния жил один вызов `render`, потому что кто угодно
(загрузка текстуры, VAO-builder) может трогать GL между кадрами. В новой
модели **все** GL-вызовы идут через `Context`, поэтому кэш можно держать
постоянно: загрузка текстуры сама обновляет кэш привязок, и кадр не начинается
с полного сброса.

Для совместной работы с чужим GL-кодом на том же контексте —
`ctx.invalidate_state()`: «кэшу больше не верить».

### 5.3 Программы и отражение

При линковке программа читает всё о себе один раз:

- атрибуты: имя → location;
- униформы вне блоков: имя → `UniformId`, тип, location, смещение в
  CPU-копии;
- сэмплеры: имя → юнит (назначаются по порядку, `uniform1i` один раз — уже
  сделано);
- uniform-блоки: имя → binding point, размер (уже сделано).

```rust
let mvp: UniformId = ctx.uniform(program, "u_mvp")?;   // один раз
```

Это развивает то, что уже есть: `active_uniform_names`, назначение юнитов и
точек по программе.

### 5.4 Параметры: группы по частоте смены

Сейчас есть batch-униформы и draw-униформы. Обобщаю это до групп параметров,
разложенных по частоте смены. Это решение ради производительности WebGL, в
первую очередь на мобильных: данные кадра грузятся один раз за проход,
смены материала сводятся к минимуму сортировкой, а на каждый draw меняется
только маленькая группа объекта. На WebGPU это тоже ложится естественно, но
целью не является: WebGPU, если будет, — отдельный крейт и отдельное решение
про общий интерфейс.

У draw до четырёх групп, по частоте смены:

| Группа | Типичное содержимое | Как часто меняется |
|---|---|---|
| 0 — кадр | камера, свет, время | раз за проход |
| 1 — материал | текстуры, цвета, параметры | между материалами |
| 2 — объект | матрица модели | на каждый draw |
| 3 — свободная | что угодно | |

Группа параметров (`BindGroupId`) — это хэндл. Внутри лежит:

- блок байтов в памяти wasm с раскладкой по `Layout` (обычные униформы и
  содержимое UBO);
- привязки: имя сэмплера → `TextureId`, имя блока → `BufferId` + диапазон.

Запись значений: по `UniformId` через API или напрямую через JS-вид
`Float32Array` на блок байтов. При отправке рендерер сравнивает группу с тем,
что уже применено, и грузит только изменённое. Для групп с UBO это один
`bufferSubData` на изменённые диапазоны.

Правило «draw видит только то, что задано в его группах» снимает протекание
униформ на уровне модели, а не проверкой.

### 5.5 Draw-список и проходы

```rust
#[repr(C)]
struct DrawItem {
    key: u64,                 // ключ сортировки
    program: ProgramId,
    state: StateId,
    mesh: MeshId,
    groups: [BindGroupId; 4],
    first: u32, count: u32, instances: u32,
}
```

- Draw-список — плоский `Vec<DrawItem>`, переиспользуется между кадрами
  (`clear` без освобождения памяти).
- Ключ сортировки составляется из программы, состояния, материала и меша
  (для прозрачного — по глубине). Сортировка по ключу группирует draw так, что
  смен состояния минимум.
- Проход — описание без владения:
  `PassDesc { target: Option<FramebufferId>, viewport, clear, invalidate }`.
- `ctx.render(&pass, &list)` — без аллокаций, только сравнение id и запись
  изменённого.

Текущая модель Pass → Batch → Draw превращается в частный случай: batch — это
общие `program`, `state` и группа 0.

## 6. API с двух сторон

Один сценарий: создать ресурсы, нарисовать кадр, удалить.

### Rust

```rust
let ctx = Context::from_canvas(&canvas, &ContextOptions::default())?;

let program = ctx.create_program(VERT, FRAG)?;
let u_model = ctx.uniform(program, "u_model")?;

let mesh = MeshBuilder::new()
    .attribute("a_pos", AttrKind::F32x3, &positions)
    .indices_u16(&indices)
    .build(&ctx)?;

let albedo = ctx.create_texture_2d(&TextureDesc::rgba8(w, h), Some(&pixels))?;
let state = ctx.state(&RenderState { depth_test: true, ..Default::default() });

let frame = ctx.create_bind_group(program, 0)?;   // камера
let material = ctx.create_bind_group(program, 1)?;
ctx.set_texture(material, "u_albedo", albedo)?;
let object = ctx.create_bind_group(program, 2)?;

let mut list = DrawList::new();

// каждый кадр
ctx.write(object, u_model, &model.to_cols_array());
list.clear();
list.push(DrawItem::indexed(program, state, mesh, [frame, material, object], 36));
ctx.render(&PassDesc::screen().clear_color([0.0, 0.0, 0.0, 1.0]), &list);

// когда больше не нужно
ctx.destroy(albedo);
```

### JS

```js
import init, { Context, DrawList } from "rswebgl";
await init();

const ctx = Context.fromCanvas(canvas);

const program = ctx.createProgram(VERT, FRAG);
const uModel = ctx.uniform(program, "u_model");

const mesh = ctx.createMesh({
  attributes: { a_pos: { format: "f32x3", data: positions } },
  indices: indices,                        // Uint16Array
});

const albedo = ctx.createTexture2D({ width: w, height: h, format: "rgba8" }, pixels);
const state = ctx.state({ depthTest: true });

const frame = ctx.createBindGroup(program, 0);
const material = ctx.createBindGroup(program, 1);
ctx.setTexture(material, "u_albedo", albedo);
const object = ctx.createBindGroup(program, 2);

const list = new DrawList();

function tick() {
  ctx.writeF32(object, uModel, modelMatrix);       // или прямо в вид:
  // ctx.view(object).set(modelMatrix, offset);
  list.clear();
  list.drawIndexed(program, state, mesh, frame, material, object, 36);
  ctx.render({ clearColor: [0, 0, 0, 1] }, list);
  requestAnimationFrame(tick);
}

ctx.destroy(albedo);   // число, free() не нужен
```

Что тут важно для JS:

- Хэндлы — числа: нечего освобождать, нечего терять, можно класть в обычные
  JS-структуры.
- Из JS-объектов, которые нужно освобождать, остаются только `Context` и
  `DrawList`, и их немного.
- Объекты-описания (`{ attributes: … }`) разбираются только при создании
  ресурсов. Вызовы на каждый кадр принимают только числа и типизированные
  массивы.

## 7. ECS: что общего, что отдельно

Это отдельная задача и отдельный документ. Здесь — только то, что нужно
решить сейчас, чтобы потом не делать дважды.

**Общее с рендерером (делаем в foundation):**

- `Entity` — тот же `Handle` с поколением. Удалённая сущность распознаётся так
  же, как удалённая текстура.
- Схемы компонентов — тот же `Layout`. Компоненты, объявленные из JS строками,
  разрешаются в `ComponentId` один раз, как униформы в `UniformId`.
- Хранилище компонентов — `Column`-ы с JS-видами. Из JS можно писать
  `Transform.position` прямо в память wasm.
- «Изменилось с прошлого кадра» — тот же учёт изменений, что для загрузки UBO.

**Мост ECS → рендерер:**

- компонент `MeshRenderer { mesh: MeshId, material: BindGroupId, … }` хранит
  только хэндлы;
- система трансформаций считает мировые матрицы из иерархии (`Parent` +
  локальные трансформации) в плотную колонку;
- система рендера отсекает невидимое, пишет матрицы в instance-буфер или в
  bind-группы объектов, заполняет и сортирует draw-список.

Вместо графа сцены, где объекты держат ссылки друг на друга, — иерархия как
данные: `Parent(Entity)` и порядок обхода, пересчитываемый при изменении.

**Открыто для ECS-документа:**

- хранилище: архетипы (как в bevy/flecs: быстрые запросы, но сущности
  переезжают между таблицами) или колонки, индексированные прямо по номеру
  сущности (как в bitECS: `Position.x[eid]`, проще всего для JS, но память под
  максимум сущностей). Склоняюсь ко второму для «горячих» компонентов вроде
  трансформаций и к разреженным множествам для редких;
- как писать системы из JS и сколько стоит переход JS ↔ wasm на систему;
- компоненты-теги и события.

## 8. Производительность: где тратится время

| Что | Цена | Что делаем |
|---|---|---|
| GL-вызов из wasm (через JS) | главная статья | кэш состояния, UBO, instancing, сортировка |
| Вызов JS → wasm | дешёвый, если аргументы числа | на горячем пути только числа и TypedArray |
| Объекты-описания из JS | разбор через serde | только при создании ресурсов |
| Строки | хэширование, сравнение | только при настройке |
| Аллокации | GC-паузы в JS, фрагментация в wasm | переиспользуемые списки, пулы |

Цель для ориентира: 10 000 draw с разными матрицами за кадр без аллокаций, где
CPU-время ядра заметно меньше времени самих GL-вызовов.

### 8.1 Мобильные устройства — главный приоритет

На мобильных узкое место обычно CPU и пропускная способность памяти, а не
шейдеры. Каждый GL-вызов в браузере проходит валидацию WebGL и часто ещё слой
ANGLE, так что на слабых телефонах счёт идёт на сотни draw за кадр, а не на
тысячи. Почти все мобильные GPU — тайловые (Mali, Adreno, PowerVR, Apple), и
им важно, когда загружать и выгружать содержимое тайлов.

Что из этого следует для дизайна:

- **Проходы с явными load/store.** Очистка в начале прохода (тайлу не нужно
  грузить старое содержимое из памяти) и `invalidateFramebuffer` в конце для
  глубины, трафарета и MSAA (тайлу не нужно их выгружать). Это уже есть в
  `Pass`; в новой модели это будут значения по умолчанию для прохода на экран.
- **Не прыгать между framebuffer туда-обратно.** Каждое переключение
  сбрасывает тайлы. Draw-список на проход и порядок проходов это
  поддерживают; в отладочной сборке можно предупреждать о повторном возврате
  к уже законченному проходу.
- **Данные объектов — одним кольцевым UBO на кадр.** Многократный
  `bufferSubData` в один и тот же UBO за кадр на мобильных драйверах может
  вызывать скрытые копии и простои. Поэтому группа «объект» по умолчанию
  пишется в общий буфер кадра (все объекты подряд, одна загрузка), а draw
  привязывает свой кусок через `bindBufferRange` с нужным выравниванием.
  Обычные униформы на draw — запасной путь для мелких случаев.
- **Instancing** для повторяющихся мешей: одна отрисовка вместо сотен.
- **Никаких синхронизаций на горячем пути:** `readPixels`, `getError`,
  `getParameter`, `checkFramebufferStatus`, `getUniformLocation` — только при
  настройке или в отладочной сборке. Релизная сборка не вызывает `getError`
  вообще.
- **Компиляция шейдеров не в первом кадре:** `KHR_parallel_shader_compile` и
  явный прогрев программ при загрузке.
- **Сжатые текстуры и половинная точность:** ETC2/ASTC через расширения
  (позже KTX2/Basis), half-float цели рендера вместо float32, `mediump` во
  фрагментных шейдерах, где хватает.
- **Разрешение рендера:** ограничение `devicePixelRatio` и масштаб
  разрешения у экранного framebuffer — самый дешёвый способ вернуть кадры на
  слабом устройстве.
- **Счётчики кадра:** число draw, смен программ и состояний, байт загрузок.
  Они почти бесплатны и сразу показывают, где тратится время на конкретном
  телефоне. Таймер GPU (`EXT_disjoint_timer_query`) на мобильных обычно
  недоступен, поэтому опираемся на эти счётчики и CPU-время.

## 9. Миграция с текущего кода

Что переезжает почти без изменений:

- трекер состояния и дифф `RenderState` → постоянный кэш (§5.2);
- проверки лимитов, правило ошибок, `warn_once`;
- потеря контекста и поколения (поколение будет у каждого слота пула, а не
  одно на весь контекст);
- раскладка std140 (`UboLayout`) → `Layout`;
- назначение юнитов и binding points по программе, `active_uniform_names` →
  отражение программы;
- glTF-транслятор: вместо `Texture`/`VertexArray` выдаёт хэндлы;
- браузерные тесты (переписываются на новый API, сценарии остаются).

Что переписывается: владение ресурсами (`Rc` → пулы), `UniformValues` → bind-
группы, `Pass`/`Batch`/`Draw` → draw-список.

Этапы, каждый со своими тестами и рабочими примерами:

1. **foundation**: `Handle`, `Pool`, `Layout`, `Column` с JS-видами и версией
   памяти.
2. **Ресурсы в пулах** + `destroy`: буферы, текстуры, renderbuffer,
   framebuffer, программы, меши.
3. **Отражение программ** + bind-группы.
4. **Draw-список**, сортировка, постоянный кэш состояния, проходы.
5. **JS-фасад**: `.d.ts`, примеры на чистом JS.
6. **glTF** на новом API.
7. **ECS** — по отдельному документу.

Старый API не поддерживаем параллельно: библиотека до 1.0, внешних
пользователей нет.

## 10. Принятые решения

1. **Хэндлы `u32`**: 20 бит индекс, 12 бит поколение. Слот с исчерпанным
   поколением выводится из оборота, поэтому старый хэндл никогда не совпадёт с
   новым объектом (§4.1).
2. **Группы параметров по частоте смены** — ради производительности WebGL,
   особенно на мобильных. WebGPU сейчас не цель: если появится, это отдельный
   крейт, а общий интерфейс над WebGL и WebGPU — отдельная задача потом.
3. **Объекты-описания в JS через serde** — только при создании ресурсов.
4. **Меш владеет своими буферами** по умолчанию; общие буферы между мешами
   поддерживаются со счётчиком использований и отложенным удалением (§5.1).
5. **Приоритет — производительность, особенно на мобильных** (§8.1).
6. **ECS — позже**, отдельным документом. Предварительно модель как в bitECS
   (колонки по номеру сущности); foundation проектируем так, чтобы она легла
   без переделок.
7. **cgtools** — проверим, когда библиотека будет примерно готова: перенесём
   пару примеров оттуда и посмотрим, как справляется.

## 11. Ход работ

**Этап 1 — foundation.** Сделан: `packages/rswebgl-foundation`.

**Этап 2 — ресурсы в пулах.** Сделан. Отличия от плана:

- Отдельного `MeshId` нет: его роль играет `VertexArrayId`. Буферы, которые
  создал `VaoBuilder`, принадлежат вершинному массиву и удаляются вместе с ним;
  чужие буферы он только использует (счётчик использований в пуле).
- Uniform-буфер владеет своим GL-буфером напрямую, а не через пул буферов.
- Постоянный кэш состояния GL (§5.2) перенесён в этап 4: пока трекер живёт
  один вызов `render`.
- `on_lost` / `on_restored` получают `&Context` аргументом: колбэку не нужно
  захватывать контекст, и нет цикла ссылок через его собственный слот.
- Через wasm-bindgen не проходит `Option<TextureId>`, поэтому геттеры
  возвращают `TextureId::NULL` вместо `None`.
- `Context` — дешёвый клон одного корня (`Rc<Core>`): это единственный общий
  указатель, он нужен асинхронным колбэкам (загрузка картинок, восстановление
  контекста).
- Пока контекст потерян, сообщения о «мёртвых» хэндлах заглушены: цикл
  рендера в это время ожидаемо обращается к старым хэндлам.

**Этап 3 — отражение программ и группы параметров.** Сделан. Отличия от плана:

- `UniformValues` удалён целиком: значения униформ приходят только из групп.
  Раскладка (`ParamLayoutId`) не привязана к программе: поля сопоставляются
  с униформами программы по имени один раз (кэш на пару программа–раскладка).
- Отдельного `UniformId` на программу нет: адресация идёт полем раскладки
  (`ParamField`, резолвится один раз из имени), а программа сама знает, куда
  это поле ложится.
- Пропуска группы целиком по версии нет: значения сравниваются с теневой
  копией в программе поле за полем. Это дёшево и корректно даже при
  пересекающихся раскладках в разных слотах.
- Раскладки и группы переживают потерю контекста (это CPU-данные); устаревают
  только хэндлы текстур и буферов внутри групп.
- Слотов 4; у draw свой слот перекрывает слот batch.

**Этап 4 — draw-список и постоянный кэш состояния.** Сделан. Отличия от плана:

- Отдельного `PassDesc` нет: `Pass` сам хранит цель, viewport, load/store и
  плоский список draw (`push`, `push_with_key`, `sort`, `clear_draws` без
  освобождения памяти). `Batch` остался как построитель: `pass.add(batch)`
  разворачивает его в элементы списка.
- `RenderState` интернируется: `ctx.render_state(&state) -> StateId`, равные
  состояния получают один id. Состояния не удаляются (их у приложения единицы).
- Ключ по умолчанию: программа (15 бит) · состояние (12) · группа слота 1
  (материал, 20) · VAO (16). Бит 63 свободен — `KEY_LAST` для прозрачного.
  Стабильность без аллокаций: `sort_unstable` по паре (ключ, порядковый номер).
- Кэш состояния (`GlState`) живёт в `Core`. Код библиотеки, который биндит вне
  рендерера (загрузка текстур, настройка VAO, индексные буферы, подключение к
  framebuffer, `check_framebuffer`), сбрасывает свою часть кэша. Потеря и
  восстановление контекста, `ctx.invalidate_state()` — весь кэш.
- Clear больше не сбрасывает render state: открываются только закрытые маски и
  scissor, после clear возвращаются. Полный `RenderState::apply` теперь ставит
  все параметры, включая выключенные тесты, — иначе следующий diff полагался
  на невыставленные значения.
- Счётчики кадра: `ctx.frame_stats()` / `reset_frame_stats()` — draw, пропуски,
  смены программ, состояний, VAO, привязки текстур и блоков, загрузки униформ.

**Этап 5 — JS-фасад.** Сделан. Отдельной обёртки на JS нет: фасад — это
сами биндинги wasm-bindgen, приведённые к виду, удобному из JS.

- Имена в JS — camelCase (`Context.fromCanvas`, `ctx.createProgram`,
  `rs.depthTest`) через `js_name`; в Rust имена прежние. Форматы сжатых
  текстур в JS названы как константы GL (`CompressedFormat.RGBA_ASTC_4X4()`).
- Аргументы-объекты (`DrawCommand`, `Viewport`, маски, `Batch`) принимаются по
  ссылке: передача по значению освобождала JS-объект, и повторное
  использование в следующем кадре падало с «null pointer passed to rust».
  `render_all(Vec<Pass>)` убран по той же причине; при постоянном кэше
  несколько `render` стоят столько же.
- Ошибки — `rswebgl::error::Error`: в Rust читается как строка (`Deref<str>`),
  в JS приходит как `Error` со стеком, а не голая строка.
- Ключ сортировки в JS — два `u32` (`pushWithKey(hi, lo, …)`): BigInt на
  каждый draw дорог.
- Пакетный путь через типизированный массив не понадобился: `push` с числами
  и ссылкой на команду не аллоцирует. Вернёмся, если замеры на телефонах
  покажут стоимость переходов JS→wasm.
- Объекты-описания через serde (`ctx.renderState({ depthTest: true })`) пока не
  сделаны: классы с camelCase-свойствами покрывают то же.
- Пример `examples/js-cube` на чистом JS, проверяется `tsc --checkJs` по
  сгенерированному `.d.ts`.

**Этап 6 — glTF, ресурсная часть.** Сделана. Сцену (иерархию, анимации) не
трогаем до ECS: загрузчик отдаёт плоский список «примитив × инстанс» с мировой
матрицей, его ECS потом и будет потреблять.

- GPU-данные делятся так же, как в документе: буфер на accessor, VAO на
  примитив меша (один раз, сколько бы узлов меш ни использовали), текстура на
  пару (картинка, сэмплер, sRGB). Индексы — в исходной ширине (u8/u16/u32).
- `EXT_mesh_gpu_instancing` (галочка «GPU Instances» в Blender): узел
  разворачивается в N элементов списка на общей геометрии. Файлы, которые
  требуют расширение (`extensionsRequired`), тоже грузятся. Отрисовка
  инстансов одним вызовом — дело рендерера, вместе с ECS.
- `DrawItem` несёт интернированный `StateId`, индексы меша, узла и инстанса.
- `Model::destroy` освобождает всё, в том числе текстуры, которые ещё
  грузятся: картинка, пришедшая после удаления, тихо отбрасывается
  (`texture_is_valid` в ядре).
- JS: `loadModel(ctx, url)` возвращает Promise с `Model`.

На Khronos-примерах: Buggy — 236 элементов на 109 мешах и 148 VAO (раньше VAO
и буферы создавались на каждый элемент); SimpleInstancing — 125 инстансов на
одном VAO.

**Ядро: сэмплеры.** Сделаны (`sampler.rs`).

- `SamplerDesc` (фильтры, wrap, LOD, compare, анизотропия) → `create_sampler`
  → `SamplerId`; явный `destroy_sampler`. Параметры в самой текстуре остаются
  запасным вариантом.
- Сэмплер живёт в группе параметров рядом с текстурой
  (`param_set_sampler(group, field, sampler)`), привязывается к тому же юниту
  и кэшируется как привязки текстур. NULL-сэмплер явно снимается с юнита,
  чтобы чужой сэмплер не протекал в следующий draw. Удалённый — сообщается,
  действуют параметры текстуры.
- Упаковщик текстур читает источники через свой LINEAR + CLAMP и больше не
  меняет их параметры. glTF: текстура на пару (картинка, sRGB), сэмплер на
  каждый различный glTF-сэмплер.

**Ядро: чтение пикселей.** Сделано (`readback.rs`).

- `read_pixels` — синхронный, ждёт GPU; для тестов и инструментов.
- `read_pixels_async` (в JS `readPixelsAsync` → Promise<Uint8Array>) не
  останавливает пайплайн: `readPixels` в PIXEL_PACK_BUFFER, `fenceSync` +
  `flush`, опрос `clientWaitSync(…, 0)` по таймеру, затем
  `getBufferSubData`. Чтение выдаётся в момент вызова, а не при первом poll
  футуры: результат — снимок на момент вызова, даже если до `await` кадр
  перерисовали. Потеря контекста во время ожидания — ошибка, а не зависание.
- Форматы: RGBA8, RGBA32F, RGBA32I, RGBA32UI — те, что WebGL2 принимает
  всегда; все с 4-байтными компонентами, поэтому pack-параметры не нужны.
- Читается через READ_FRAMEBUFFER: цель рисования и её кэш не трогаются.

**Ядро: копирование.** Сделано (`copy.rs`).

- MSAA-resolve — операция прохода: `pass.set_resolve(dst)` копирует цвет 0 в
  текстуру или canvas сразу после draw, затем `set_invalidate` отбрасывает
  сэмплы — на тайловых GPU они не покидают тайловую память. После resolve обе
  привязки (READ и DRAW) указывают на цель resolve, кэш знает об этом.
- `blit_framebuffer` (масштабирование, ручной resolve), `copy_buffer`
  (`copyBufferSubData`; индексные буферы WebGL не пускает на copy-цели),
  `copy_texture_sub_image_2d`. Отклонённая операция — console.error и no-op.
- Чтение буфера: `buffer_read` / `buffer_read_async` — асинхронное копирует
  диапазон в scratch-буфер в момент вызова и ждёт fence.
- `js-cube` рендерит через 4× MSAA-фреймбуфер с resolve в canvas
  (canvas без встроенного antialias), M переключает.

**Ядро: float-цели рендера.** Сделаны (`float_targets.rs`).

- Контекст при создании включает то, что есть на устройстве:
  `EXT_color_buffer_float`, `EXT_color_buffer_half_float` (16F на мобильных),
  `OES_texture_float_linear`, `EXT_float_blend`. Пока не используются — ничего
  не стоят; после restore включаются снова.
- Float-рендербуфер, который устройство не умеет, — ошибка при создании;
  такая текстура в цветовом слоте — console.error и no-op. В обоих случаях
  с названием недостающего расширения, вместо молча неполного фреймбуфера.
- `can_render_to(format)` / `can_render_to_renderbuffer` — выбрать формат
  заранее (RGBA16F, иначе RGBA8); `can_filter_float32`. 32F-текстура с
  линейной фильтрацией без `OES_texture_float_linear` — предупреждение при
  выделении storage.

**Ядро: запросы.** Сделаны (`query.rs`).

- `QueryId` в пуле, явный `destroy_query`. Запрос привязан к тому, что
  измеряет: occlusion (`AnySamplesPassed*`) — к одному draw
  (`pass.set_last_draw_query`), таймер (`TimeElapsed`) — ко всему проходу
  (`pass.set_timer`). Рендерер сам делает begin/end, поэтому вложить запросы
  неправильно нельзя; запрос не того вида — сообщение один раз, работа
  выполняется без измерения.
- Результат WebGL не отдаёт в том же кадре: `query_result` (опрос, None пока
  не готов) или `query_result_async` (Promise). Результат хранится до
  следующего запуска. Таймер, который GPU сбил (`GPU_DISJOINT_EXT`),
  результата не имеет.
- Таймеры требуют `EXT_disjoint_timer_query_webgl2`, браузеры его часто
  скрывают: `can_time_gpu`, а `create_query(TimeElapsed)` без него — ошибка.

**Ядро: transform feedback.** Сделан (`feedback.rs`).

- Программа объявляет захватываемые varyings при создании
  (`create_program_with_feedback`, Interleaved или Separate); объект
  `FeedbackId` держит буферы (`transform_feedback_set_buffer[_range]`,
  удерживает их как вложения фреймбуфера); проход пишет в него
  (`pass.set_transform_feedback(tf, mode, discard)`). Рендерер начинает запись
  перед первым draw и заканчивает после последнего, так что draw-вызовы
  дописывают подряд; после прохода объект отвязан, и буфер — обычный источник
  вершин (ping-pong для частиц).
- Правила WebGL2 проверяются для каждого draw с причиной вместо GL-ошибки:
  режим равен режиму записи (Points / Lines / Triangles), только
  неиндексированные draw (indexed — INVALID_OPERATION, проверено), одна
  программа на запись, все записываемые буферы привязаны, нет выхода за конец
  буфера (размер считается из типов varyings).
- `QueryKind::TransformFeedbackPrimitivesWritten` через
  `pass.set_transform_feedback_query`.

Ядро WebGL2 покрыто целиком.
