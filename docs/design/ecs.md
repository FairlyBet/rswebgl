# ECS и сцена

Статус: E1 сделан (`packages/rswebgl-ecs`), E2–E4 и E5a сделаны (`packages/rswebgl-scene`).

Продолжение §7 `architecture.md`: что там оставлено «для ECS-документа»,
решается здесь.

## 1. Для чего

Главный потребитель — вьювер (ювелирные изделия, glTF-модели), встроенный в
JS-сайт. Отсюда масштаб и требования:

- сущностей сотни – десятки тысяч, не миллионы. Частицы и толпы — не
  сущности, а instancing / transform feedback внутри одной сущности;
- сцена в основном статична: модель загрузили, крутим камеру, иногда меняем
  материал, вариант камня, двигаем часть. Кадр без изменений должен стоить
  почти ноль на CPU;
- JS управляет сценой: создать/удалить объект, поставить трансформацию,
  сменить материал, узнать мировую матрицу. Без `.free()` и без объекта на
  каждую сущность;
- это не игровой движок: нет планировщика систем, параллелизма, событий
  общего вида.

## 2. Крейты

```
rswebgl-foundation   хэндлы, пулы, колонки, учёт изменений (есть)
rswebgl-ecs          мир, сущности, хранилище компонентов, запросы
                     (зависит только от foundation; рендерер не знает)
rswebgl-scene        компоненты сцены и системы: трансформации, иерархия,
                     камера, свет, MeshRenderer, отсечение, сборка Pass;
                     glTF → сущности (зависит от ecs, rswebgl, rswebgl-gltf)
```

Как в §3: рендерер без ECS работает, ECS без рендерера тоже. Мост — только
`rswebgl-scene`. Математика — `glam` (wasm-дружелюбная, без аллокаций).

## 3. Сущности

`Entity` — тот же `Handle` из foundation: `u32`, 20 бит индекс (1M живых),
12 бит поколение, исчерпанный слот выводится из оборота. В JS — `number`.

53-битный id (§4.1) не нужен: при масштабе из §1 миллиона живых хватает, а
частицы сущностями не будут. Один формат хэндла для ресурсов и сущностей.

## 4. Хранилище: разреженные множества

Варианты из §7: архетипы (bevy/flecs) или колонки по номеру сущности (bitECS).
Предлагаю третий, проще обоих — **разреженное множество на компонент**
(как в EnTT):

```
sparse: Vec<u32>          индекс сущности → строка (или NONE)
entities: Vec<Entity>     строка → сущность
columns: [Column]         плотные данные по строкам (SoA, из foundation)
changed: Vec<u32>         строка → тик последнего изменения
```

- добавить/удалить компонент — O(1) (удаление переносит последнюю строку на
  место удалённой); сущность никуда не переезжает, в отличие от архетипов;
- обход — по плотным колонкам, без дыр; память ∝ числу сущностей с
  компонентом, а не максимуму сущностей (минус bitECS для редких компонентов
  вроде Camera/Light);
- запрос по двум компонентам: обходим меньшее множество и смотрим во второе
  через `sparse` — для наших масштабов достаточно;
- JS получает те же виды, что у колонок foundation: `Float32Array` по
  плотным данным + `world.row(component, entity)`.

Архетипы дали бы более быстрые запросы по многим компонентам сразу, но ценой
переездов сущностей и сложности, которая на тысячах объектов не окупится.

## 5. Компоненты

**Встроенные (Rust, типизированные):** `Transform` (позиция, кватернион,
масштаб), `Parent`, `WorldMatrix`, `MeshRenderer` (VAO + материал-группа +
состояние + команда), `Bounds` (локальный AABB), `Camera`, `Light`, `Visible`.

**Свои из JS** — позже (этап E5): схема строками через `Layout`
(`world.defineComponent("Spin", { speed: "f32" })`), колонки из foundation.
Для вьювера на старте не нужны: JS управляет встроенными компонентами.

## 6. Учёт изменений

Тики, как в bevy: у мира счётчик кадров, у каждой строки — тик последней
записи. Система помнит, на каком тике была в прошлый раз, и обрабатывает
только изменённое. Запись из Rust ставит тик сама; запись из JS через вид —
`world.markChanged(component, entity)` (или по диапазону строк), как
`mark_dirty` у колонок.

Это и даёт «статичный кадр почти бесплатно»: ни одна трансформация не
изменилась — пересчёта матриц нет, только сборка draw-списка.

## 7. Иерархия

`Parent(Entity)` — данные, не ссылки. Система трансформаций держит порядок
обхода (родители раньше детей), пересчитываемый только когда меняется
какой-то `Parent`. Мировая матрица пересчитывается у изменённых `Transform`
и всего их поддерева. Удаление сущности удаляет её поддерево (рекурсивно,
явно — `despawn_recursive`), чтобы не оставлять детей с мёртвым родителем.

## 8. Системы и кадр

Систем немного, они — обычные функции, порядок задаёт приложение. Из JS кадр
— несколько вызовов, а не вызов на объект:

```js
world.updateTransforms();          // иерархия → WorldMatrix
scene.render(ctx, camera, pass);   // отсечение по frustum, матрицы в группы
                                   // объектов, draw-список, сортировка
ctx.render(pass);
```

Сборка draw-списка — в существующий `Pass`: ключ сортировки, группы
параметров по слотам (0 кадр — UBO камеры/света, 1 материал, 2 объект).
Матрица объекта пишется в его группу только если `WorldMatrix` изменилась.

## 9. Этапы

- **E1 — ECS-ядро** (`rswebgl-ecs`): сущности, разреженные множества,
  типизированные компоненты, запросы по 1–2 компонентам, тики. Тесты на хосте
  (без браузера).
- **E2 — трансформации и иерархия** (`rswebgl-scene`): `Transform`, `Parent`,
  `WorldMatrix`, система, `despawn_recursive`.
- **E3 — рендер сцены**: `MeshRenderer`, `Camera`, `Bounds`, отсечение,
  сборка `Pass`, UBO кадра. Пример: сетка кубов из `js-cube` через сцену.
- **E4 — glTF в сцену и JS-фасад**: узлы glTF → сущности с иерархией,
  `loadModel` возвращает корневую сущность; JS-API сцены.
- **E5 — PBR**, по шагам:
  - **E5a** — шейдер Cook-Torrance с вариантами под примитив и материал,
    полные материалы glTF, сущности-источники света, тонмаппинг, прозрачные
    draw'ы от дальних к ближним;
  - **E5b** — IBL: HDR-окружение → irradiance, prefiltered cubemap, BRDF LUT;
    фон;
  - **E5c** — расширения для ювелирки: transmission, ior, volume, specular,
    clearcoat (камни, металлы);
  - **E5d** — вьювер из cgtools.
  Свои компоненты из JS — по необходимости.

**E1 — сделан.** `World`, `Entity` (typed_handle поверх `Handle`), `Storage<T>`
(разреженное множество: `sparse` / `entities` / `data` / `changed` + журнал
удалений). Отличия от плана и детали:

- Компонент — любой `'static` тип, хранилище создаётся при первом
  использовании; данные строк — `Vec<T>` (AoS), а не колонки foundation:
  для типизированных Rust-компонентов так проще, а `#[repr(C)]` из f32 всё
  равно видится из JS одним `Float32Array` (сделаем в E4).
- Тики `u64`. Правило системы: `let now = world.advance_tick()` (возвращает
  текущий тик и сдвигает мир), обработать изменённое после `last_run`,
  свои записи ставить тиком `now`, затем `last_run = now`. Так записи
  после прогона системы видны ей в следующий раз, а её собственные — нет.
- `Mut<T>` помечает изменение только при записи через `DerefMut`;
  `set_if_neq` не помечает равное значение.
- Удаления (`remove`, `despawn`) пишутся в `Storage::removed` до
  `World::clear_trackers()` — раз в кадр, после систем.
- Запросы: `join::<A, B>()` для чтения (обход по `A`), для записи —
  `storages_mut::<A, B>()` и обычный цикл. Без RefCell.
- Тесты на хосте (`cargo test -p rswebgl-ecs`), браузер не нужен.

**E2 — сделан.** `rswebgl-scene` (пока зависит только от `rswebgl-ecs` и
`glam`; рендерер подключится в E3): `Transform` (позиция, кватернион,
масштаб; `from_matrix` для узлов glTF), `Parent(Entity)`, `WorldMatrix`.

- `TransformSystem::update(&mut world)` — раз в кадр **до**
  `clear_trackers` (удаления видны через журналы). Порядок «родители раньше
  детей» кэшируется и перестраивается (подсчётной сортировкой + обход в
  ширину, без аллокаций в установившемся режиме), только если изменился
  какой-то `Parent`, добавился/удалился `Transform` или удалена сущность.
  После перестройки пересчитывается всё; иначе — изменённые `Transform` и их
  поддеревья. Кадр без движения ничего не пишет; `update` возвращает число
  пересчитанных матриц.
- `WorldMatrix` добавляет и пишет только система; записи помечены её тиком,
  так что рендер в E3 возьмёт только сдвинувшиеся объекты (`iter_changed`).
- Родитель мёртв или без `Transform` — сущность считается корнем.
- `set_parent` отказывает в циклах и мёртвых сущностях; повторная установка
  того же родителя не считается изменением. Цикл, вставленный напрямую
  через `Parent`, не зацикливает систему: такие сущности пропускаются
  (`skipped()`).
- `despawn_recursive` удаляет поддерево (карта детей строится один раз),
  `children` — разовый запрос, не для покадровых циклов.
- Тесты на хосте (`cargo test -p rswebgl-scene`).

**E3 — сделан.** `rswebgl-scene` подключает рендерер.

- Компоненты: `Camera` (перспектива / орто, `aspect` задаёт приложение;
  вид — обратная `WorldMatrix` сущности камеры), `Bounds` (локальный AABB;
  без него сущность не отсекается), `MeshRenderer` (программа, состояние,
  VAO, группа материала, команда — хэндлы рендерера, сцена их не создаёт и
  не удаляет), `Visible(bool)` (в E4 стал наследуемым: скрытый предок
  скрывает поддерево).
- `SceneRenderer::render(&world, &ctx, camera, &mut pass)` — после
  `TransformSystem::update`, до `clear_trackers`: пишет матрицы камеры в
  UBO блока `Frame` (`u_view`, `u_proj`, `u_view_proj`, `u_camera_pos`),
  отсекает по frustum (AABB, переведённый в мир по модулю матрицы) и
  добавляет draw'ы в `Pass` с группами: 0 — кадр, 1 — материал, 2 — объект
  (`u_model`, `u_normal_matrix`). Пасс не чистит и не сортирует — это
  приложение (`clear_draws` / `sort`), чтобы можно было добавить свои
  draw'ы.
- Группа объекта создаётся при первой отрисовке и перезаписывается, только
  если её `WorldMatrix` изменилась. «Изменилась» считается по тику,
  записанному в саму группу, а не по прошлому прогону: отсечённый объект не
  пишется, и когда он возвращается в кадр (сдвинулась камера), его группа
  догоняет.
- Группы сущностей без `MeshRenderer` (снят, сущность удалена)
  уничтожаются на следующем `render` — по журналу удалений и, на всякий
  случай, сверкой числа. `destroy(ctx)` освобождает всё; после потери
  контекста — новый `SceneRenderer`.
- `render` возвращает `RenderStats { drawn, culled, objects_written }`.
- Тесты: отсечение и камеры на хосте, сам рендер — в браузере
  (`wasm-pack test --headless --chrome packages/rswebgl-scene`).
  Пример `examples/scene` (`trunk serve`): сетка 24×24 кубов на
  вращающемся pivot, половина ещё крутится сама.

**E4 — сделан.** glTF в сцену и JS-фасад.

- `rswebgl-gltf` дополнительно отдаёт дерево узлов сцены (`Model::nodes()`:
  локальная матрица, родитель, имя; родители раньше детей), а у
  `DrawItem` — локальный AABB примитива и матрицу инстанса
  `EXT_mesh_gpu_instancing` относительно узла.
- `spawn_model(world, &model, program)` → корневая сущность: узел glTF —
  сущность с `Transform`, `Parent`, `Name`; примитив — дочерняя сущность
  узла с `MeshRenderer`, `Bounds` и матрицей инстанса в `Transform`.
  `find_by_name(world, root, name)` — найти деталь (камень, оправу).
- `Visible(false)` теперь наследуется: скрыть узел = скрыть его примитивы.
  Предки обходятся только пока в мире есть хоть один `Visible(false)`.
- **JS: класс `Scene`** (`rswebgl-scene` собирается как cdylib — рендерер,
  загрузчик glTF и сцена в одном модуле). Владеет `World`,
  `TransformSystem`, `SceneRenderer`. Сущности — числа, компоненты —
  методами по сущности (`setTranslation`, `setRotation[Euler]`, `setScale`,
  `setLocalMatrix`, `lookAt`, `setParent`, `setPerspectiveCamera`,
  `setCameraAspect`, `setMesh`, `setMaterial`, `setBounds`, `setVisible`,
  `findByName`, `worldMatrix`, …). Мёртвая сущность — `console.error` один
  раз и no-op; цикл в `setParent` — `false` + ошибка.
- `scene.addModel(model, program)` забирает `Model` (в JS объект
  поглощается — `.free()` не нужен); `scene.despawn(root)` удаляет поддерево
  и GPU-ресурсы модели; `modelBounds(root)` — сфера для кадрирования камеры.
- Кадр из JS: `pass.clearDraws(); scene.render(camera, pass); pass.sort();
  ctx.render(pass)` — `render` сам обновляет трансформации и чистит трекеры.
- Тесты в браузере (`tests/model.rs`): модель из data-URL, имена, иерархия,
  сдвиг узла/корня, наследуемая видимость, освобождение ресурсов.
  Пример `examples/js-scene`: модель glTF на поворотном столе из чистого JS.

**E5a — сделан.** PBR-ядро.

- `rswebgl-gltf`: у примитива — флаги атрибутов (`ATTR_*`: NORMAL, UV0,
  TANGENT, COLOR_0, UV1; TEXCOORD_1 теперь на location 5); у материала —
  все пять карт с их наборами UV и семплерами, `normalTexture.scale`,
  `occlusionTexture.strength`, `KHR_materials_emissive_strength`,
  `KHR_materials_unlit`. Группа материала несёт всё это (имена — в
  документации `Model`).
- `rswebgl-scene/shaders/pbr.{vert,frag}` — BRDF из приложения B спецификации
  glTF (GGX, height-correlated Smith, Schlick, Lambert), пунктуальные
  источники в единицах `KHR_lights_punctual`, постоянный ambient с
  аналитическим env-BRDF (до IBL), эмиссия, альфа-режимы, экспозиция,
  тонмаппер Khronos PBR Neutral, sRGB. Без касательных нормальная карта
  берёт базис из производных.
- `PbrShaders`: вариант на `PbrKey` (атрибуты × карты × UV1 × альфа ×
  unlit), компиляция при первом использовании. `spawn_model` принимает
  выбор программы на примитив; `Scene.addModel(model)` — встроенный PBR,
  `addModelWithProgram` — свой шейдер.
- `Light` (directional / point / spot) — компонент: светит вдоль −Z
  сущности из её позиции. `SceneRenderer` пишет до 8 источников, ambient и
  экспозицию в блок `Lighting` (рядом с `Frame` в слоте 0) — только когда
  что-то изменилось. Скрытые (`Visible(false)`) источники не светят.
- `MeshRenderer.transparent`: такие draw'ы идут после непрозрачных,
  от дальних к ближним (ключ `KEY_LAST` + расстояние до центра bounds).
  Для glTF — по `alphaMode: BLEND`.
- JS: `setDirectionalLight` / `setPointLight` / `setSpotLight` /
  `removeLight`, `setAmbient`, `setExposure`, `setTransparent`,
  `shaderVariantCount`.
- Тесты в браузере (`tests/pbr.rs`): все признаки компилируются и линкуются
  (по одному, все сразу, карты на UV1); направленный и точечный свет,
  дальность, цвет, unlit, эмиссия, экспозиция; порядок прозрачных.
  Пример `examples/js-scene` — DamagedHelmet со всеми картами и тремя
  источниками.
